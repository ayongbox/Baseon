# ADR-0003 · 框架承载机制，业务通过 SPI 提供策略

- **状态**：已采纳（9 期数据权限完整落地）
- **日期**：2026-10-28
- **决策者**：脚手架维护者
- **关联**：`core.spi`、`baseon-starter-data-scope`、`baseon-starter-cache`、`baseon-starter-tenant`

## 背景

数据权限、缓存 key 前缀、租户策略等能力有一个共同点：**拦截与改写机制是通用的，具体规则因业务而异**。如果把规则硬编码进 Starter：

- 一个业务的需求会污染所有使用方；
- 规则变更需要发版框架，无法由业务自行调整；
- 框架无法判断「空集合」与「不限制」的语义差异，容易静默放行。

## 决策

1. Starter 只实现机制：SQL 改写、序列化裁剪、缓存前缀拼接、租户过滤等；
2. 业务策略通过 `core.spi` 的 Provider 注入，框架只定义契约：
   - `DataScopeProvider`：`visibleIds()` / `column()` / `visibleFields()`；
   - `CacheKeyPrefixProvider`：返回业务自定义 key 前缀；
   - 租户等策略通过编程式 API（`TenantOps`）与上下文提供，不内置业务规则；
3. 语义固定并写入文档：
   - **空集 = 查不到数据**（生成永假条件），**null = 不限制**（放行）；
   - 未提供 Provider 时默认放行；`strict` 模式改为启动失败，供权限强约束场景使用；
4. Provider 缺失不阻断 Starter 装配，避免「没配权限就起不来」；需要强约束时显式开启 strict。

## 后果

### 正面

- 框架升级不改变业务规则，业务规则变更不发版框架；
- 权限漏配可通过 strict 变成启动失败，避免静默越权；
- 同一套机制可复用到不同业务线，实现类互不感知。

### 负面 / 代价

- 业务必须理解空集/null 语义，误用会造成「查不到数据」或「越权」；
- Provider 实现质量不在框架控制范围，需要业务测试覆盖；
- SPI 数量增长会增加内核表面积，新增 SPI 需评审。

## 备选方案

| 方案 | 放弃原因 |
|---|---|
| 在 Starter 内置基于注解参数的规则 | 表达能力有限，复杂条件仍需回调，最终退化为 SPI |
| 引入规则引擎（如 Drools/QLExpress） | 增加运行期依赖与安全面，SQL 改写场景仍需 AST 操作 |
| 把权限规则放配置文件 | 无法表达动态集合（如「本人 + 下属」），且配置无法单测 |

## 验证方式

- `DataScopeProvider` 契约有 H2 集成测试覆盖 6 个场景（空集、null、字段裁剪等）；
- `baseon-starter-data-scope` 的 ArchUnit 规则通过；
- `strict=true` 且无 Provider 时启动失败有测试断言。
